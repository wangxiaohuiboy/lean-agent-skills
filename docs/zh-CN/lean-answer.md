# lean-answer

> 先给答案。开场白、复述、事后总结，全是成本。

## 它解决什么问题

输出 token 和输入 token 一样计费，而读的人正在任务中间——他要的是结果，不是一段关于结果的话。最常见的浪费：

- 「好问题！」「我很乐意帮你处理这个。」
- 在回答之前先把用户的请求复述一遍。
- 收尾时再讲一遍刚才做了什么：「我已经按你的要求更新了文件，添加了重试逻辑。」
- 把即将执行的工具调用讲一遍。
- 层层叠加的模糊措辞：「或许可能值得考虑一下是否……」。

## 什么时候会触发

你要求简洁的时候、连续问一堆小问题的时候，或者纯粹希望回复短一点的时候。

## 核心规则

1. **结论先行。**第一句给结果、命令或决定。理由放后面，且只放读者判断可信度所需的部分。
2. **引用代替粘贴。**给 `src/api/retry.ts:142`，不要贴函数体。贴一行，别贴整个函数。读者自己开着仓库的时候，`git diff --stat` 往往就够了。
3. **结构跟着内容走。**一个事实 → 一句话。一个带原因的决定 → 决定 + 一行原因。三件以上可比较的东西 → 表格。用户要照着执行的步骤 → 编号列表，每条一个动作。给三行回复配小标题是纯浪费。
4. **不确定就直说，但用从句说。**「Windows 上没测过」五个字够了，不要写一段免责声明。不改变读者下一步动作的免责声明都是填料。
5. **语言跟随用户。**用户用中文就用中文回。代码、标识符、文件路径、日志保持原样。

## 不能省略的部分

简洁永远不适用于：**精确的命令**、需要用户去匹配的**报错信息**、**破坏性变更警告**、安全或数据丢失的后果、以及**某个看起来可行的方案为什么不行的原因**。

压的是文字，不是事实。

## 什么情况下别用它

用户要的是完整讲解、教程、设计文档、或逐行分析的时候。那时候的冗长是价值本身，不是浪费。

## 效果对比

**默认**：

> 好问题！我看了你的 `server.ts`，发现第 143 行的 `parseOptions` 在收到空字符串时没有回退到默认值，这会导致……我已经修改了该文件，现在它会在空字符串时使用默认值了。如果你还有其他问题随时告诉我！

**这个 skill**：

> 空字符串绕过了 `server.ts:143` 的默认值回退，已修。
>
> 没动 `parseArgs` 里的同类问题——它调用的 `parseOptions` 已覆盖，无需重复加。

第二版信息更多（多了「同类问题为什么不用改」），字数不到一半。

## 怎么改成适合你的

这条最容易按个人偏好调：有人完全不要「我做了什么」的总结，有人需要它来确认 agent 理解对了。先按默认来，发现自己在反复删同一类句子，就把那类句子加进「删掉」清单——**写具体的句子模式比写「简洁一点」有效**。
