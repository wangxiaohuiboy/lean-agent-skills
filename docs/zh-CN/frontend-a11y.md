# frontend-a11y

> 按优先级排好的一轮 WCAG 2.2 AA 检查。键盘走查排第一，因为它抓到的问题比所有自动化工具加起来还多。

## 它解决什么问题

无障碍检查最常见的失败方式不是「没做」，而是**做错了顺序**：先跑一遍 axe、把报告里的红色项修掉、然后宣布通过。而 axe 类工具大约只能覆盖真实问题的三分之一，剩下的——焦点顺序、键盘陷阱、焦点丢失、错误信息没被朗读——全在工具的盲区里。

## 什么时候会触发

上线 UI、review 组件、有人反馈「用不了 / 读不出来 / 键盘走不过去」。

## 检查顺序（按命中率排的）

### 1. 键盘走查

只用 Tab、Shift+Tab、Enter、Space、Escape 和方向键完成每一个任务。

- 每个可交互元素都能到达、能操作。
- DOM 顺序和视觉顺序一致。**`tabindex` 大于 0 是 bug，不是修法。**
- 没有键盘陷阱。Escape 关闭弹窗和菜单，焦点回到打开它的元素。
- 长导航之前有跳转链接。
- 自定义组件遵循它对应的按键约定（单选组/标签页/列表框用方向键）。

### 2. 语义优先于 ARIA

用本来就干这事的原生元素：`button`、`a[href]`、`input`、`label`、`dialog`、`details`、`fieldset`。**没有 ARIA 好过错误的 ARIA。**

- 不要给 `div`/`span` 加 `onClick` 就完事——要么换成 `button`，要么补齐 role、`tabindex` 和键盘处理。**直接换成 `button` 才是修法，`role="button"` 不是。**
- 不要给任何可获得焦点的元素加 `aria-hidden="true"`。
- 用语义化地标（`main`/`nav`/`header`/`footer`），每页一个 `h1`，标题层级按顺序，不要为了字级跳级。

### 3. 可访问名称

- 每个控件都要有程序可读的名称。纯图标按钮需要 `aria-label`，有空间时优先用可见文字标签。
- 图片：装饰性用 `alt=""`，有意义的描述功能或内容，不要写「image of」。
- 链接要说清去哪：「查看发票 42」，不要写「点击这里」「了解更多」——屏幕阅读器用户是靠链接列表导航的。
- **控件上的 `aria-label` 必须以可见文字开头**，否则语音控制叫不出这个控件。

### 4. 焦点

- 永远不要在没有可见替代的情况下写 `outline: none`。用 `:focus-visible`：指针用户看不到焦点环，键盘用户永远看得到。
- 主动移动焦点：弹窗打开时移进去、路由切换时移到新标题或主内容、关闭时回到触发元素。
- 用 `tabindex="-1"` 作为程序化聚焦目标，绝不用 `tabindex="0"`。
- 用原生 `<dialog>` 或成熟的基础组件库——焦点陷阱、Escape、背景 inert 都是白送的。

### 5. 表单与错误

- 每个输入都有用 `for`/`id` 绑定到它的 `<label>`。**placeholder 不是 label。**
- 错误要说清问题和修法，用 `aria-describedby` 关联，保留用户输入，消息放在字段附近。
- 在提交或失焦时校验，不要每敲一个字就校验。
- 标注必填项；用 `type`、`inputmode`、`autocomplete` 让移动端键盘和密码管理器正常工作。
- 相关控件用 `fieldset`/`legend` 分组。不能只用颜色传达的状态，必须有文字或带文字的图标。

### 6. 对比度与文字

- 正文最低 4.5:1；大号文字（24px，或 19px 粗体）、UI 描边、图标、焦点指示器最低 3:1。
- **placeholder、disabled、二级文字是重灾区**，一并检查。
- 200% 缩放下、320px 宽度下要可用，不能横向滚动、不能被裁切。
- 禁止 `user-scalable=no` 或 `maximum-scale=1`。
- 字号用 `rem`，文字容器不设固定高度，用户放大字体时才不会裁字。

### 7. 动效与时间

- 尊重 `prefers-reduced-motion`，给真正的降级状态而不是坏掉的动画。
- 超过 5 秒的自动播放动效要能暂停或停止。
- 每秒闪烁不超过三次。

### 8. 实时区域（live region）

- 状态更新、计数、不紧急的提示用 `aria-live="polite"`。
- 需要打断用户的错误才用 `assertive` 或 `role="alert"`。
- 区域必须先存在于 DOM 里再改内容，否则播报会被漏掉。
- 不要包住页面加载时就渲染的内容——那会导致每次访问都播报一遍。

## 怎么算做完了

自动化工具（axe、Lighthouse、Lighthouse CI）是**地板，不是验收**。每一轮检查都要自己跑一遍第 1 节的键盘走查；流程复杂时用屏幕阅读器抽查（macOS 用 VoiceOver：`Cmd+F5` 打开，`Ctrl+Option+U` 打开转子；Windows 用 NVDA）。

报告格式：**`路径:行号` + WCAG 条款 + 具体修法**。

> 缺少可访问名称（WCAG 4.1.2）—— 加 `aria-label="关闭对话框"`

这样是可执行的。「需要改进无障碍」不是。

## 什么情况下别用它

原生桌面或移动 App 的无障碍不在范围内。

## 和 frontend-craft 的关系

当修法本身是个设计决定而不是缺陷时（例如唯一合适的可访问标签太长、放不进布局），配合 `frontend-craft` 一起看——那是布局要改，不是 `aria-label` 要加长。

## 怎么改成适合你的

- **把报告格式固定下来**（`路径:行号 + 条款 + 修法`），比要求「写详细点」有用，因为它在 review 里是可核对的结构。
- 如果你们有指定的屏幕阅读器或目标用户群（比如政务项目对 4.5:1 和缩放的要求更硬），把对应条款的验收标准写具体。
- 如果 CI 里已经跑了 axe，把「自动化工具是地板不是验收」这句改写成你们真实的门禁（例如「axe 零 error 才允许合并，键盘走查由 PR 作者在描述里勾选」）。
