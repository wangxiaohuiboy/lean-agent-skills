# lean-context

> 每次读文件之前，先能说清这次要回答什么问题。能搜就不读，能读一段就不读整个文件。

## 它解决什么问题

Agent 最贵的开销不是写代码，是**读进来的上下文会在此后每一轮里重复计费**。一次 900 行的全文件读取，不只花一次钱，而是从读进来的那一刻起，后面每一次工具调用、每一次推理都在为它付费。

典型浪费，都真实发生：

- 为了看其中一个函数，把整个文件读进来。
- 已经读过的文件，或者刚刚编辑过的文件，再读一遍「确认一下」。
- 五个互相独立的查询排成五轮对话，每一轮都把前面的对话前缀重新发一次。
- 把构建日志、lockfile、打包产物倒进上下文。

## 什么时候会触发

在陌生或大型仓库里定位问题时：追一个 bug、找一个符号的定义、查一条调用链。以及上下文快满、需要控制读取量的时候。

## 核心规则

1. **每次读都要挂一个「要回答的问题」。**「让我看看这个文件是干嘛的」不算问题；「`--retry` 是在哪里解析的」才算。说不出来就别读。
2. **四步阶梯，停在第一个能回答问题的步骤**：全局搜索 → 只列声明不读函数体 → 只读相关区间 → 最后才考虑读整个文件，而且先 `wc -l` 量一下。
3. **独立查询合并成一批并行发出。**信息量相同的情况下，五轮往返的成本远高于一轮。
4. **在源头裁输出**：`rg -l` 只要文件列表、`rg -c` 只要计数、`sed -n '1,80p'` 只要前 80 行、`--stat` 先看形状。
5. **不重复读。**包括刚编辑过的文件——编辑结果本身就是确认。
6. **边走边压缩**，只保留 `路径:行号 — 做什么 — 为什么要紧` 这个提炼形式，丢掉原始输出。
7. **知道什么时候停。**能说出（a）改动落在哪里、（b）谁会调用它，就停止探索。

## 它明确不允许的事

这不是「少读一点保险一点」，而是有清晰的禁止项：

- 递归读完一个入口点 import 的每一个模块。
- 没量过大小就 `cat`。
- 为了了解一个函数的行为去读测试，而不是读函数本身。
- 从 home 目录或 `.git` 开始做全盘 `find`。
- 让 agent「通读整个代码库然后总结一下」，而不是问一个具体问题。

lockfile、构建产物、压缩后的 bundle、生成的 migration，只有在故障**就在里面**的时候才读，而且要限定到具体行。

## 效果对比

**没有这个 skill**：为了改一个 CLI 参数，读 `src/cli.ts`（900 行），再读它 import 的 `src/config.ts` 和 `src/types.ts`，共约 1400 行。

**有**：`rg -n 'retry' src/cli.ts` → 命中 143 行 → `sed -n '135,160p'` → 结束，约 25 行。

## 怎么改成适合你的

`references/commands.md` 是一份命令速查表。如果你的环境里没有 `ripgrep`、用的是 `git grep` / `ag` / 别的搜索工具，把那份表换成你自己环境的命令——这是最容易按本地习惯调整的一处。

如果你在团队里推这个 skill，值得额外加一条：明确写出「不要读」的目录（构建产物、vendor、生成代码），比讲道理有效。
