# context-handoff

> 把长会话压成一页能续接的简报。下一个会话、下一个人，不需要读聊天记录。

## 它解决什么问题

长任务停下来再继续时只有两种糟糕选择：把整段历史复制到新对话里（贵，而且噪声大），或者只带关键结论过去（便宜，但一定会漏东西）。

漏掉代价最高的一类信息，恰恰是最没人记录的一类：**试过并且失败的路**。不写下来，下一个会话就会用同样的方法再撞一次墙，而它甚至不知道自己撞过。

## 什么时候会触发

上下文快满的时候、任务中途暂停的时候、要换一个新对话继续的时候、交接给同事的时候。

## 简报结构

必有的五节：

```markdown
## 目标
<一句话，加上验收标准——怎么算做完了>

## 状态
- 已完成：<落地的内容 + 文件路径或 commit sha>
- 进行中：<精确停在哪，path:line>
- 未开始：<剩余部分，按顺序>

## 决策
- <决定> — <迫使你这么做的那条约束>
  只写会约束未来工作的决策，成本可忽略的可逆决定直接丢掉。

## 试过且失败
- <方案> — <为什么失败>
  这一节价值最高，它决定下一个会话会不会重做无用功。

## 下一步动作
<精确到可以直接执行的下一条命令或编辑>
```

按需再加两节：**地雷**（看起来对但其实不对的东西：不稳定的测试、不能手改的生成文件、已经对 staging 执行过的迁移、缓存的构建产物）和**未验证**（从没真正验证过的结论，标出来，避免下一个会话继承虚假的确定性）。

## 核心规则

- **给指针，不给内容。**`src/api/retry.ts:44`，不是函数体。`git diff 4f2a9c1`，不是 diff 本身。
- **用精确标识符。**分支名、commit sha、环境变量名、端口、migration id、feature flag 的确切拼写。描述会被记错，标识符不会。
- **必须写失败的路。**省略死胡同的简报是个陷阱。
- **不要叙事。**没有「我先看了……然后我决定……」。
- **把没验证的标成未验证。**测试写了但没跑、代码通过了编译但从没实际执行过，都要写清楚。
- **写清哪些文件别碰**，如果有陷阱文件、生成产物，或者某个跑起来很慢、应该避开的命令。

## 长度纪律

超过一页，就说明它在搬运本该存在于仓库里的细节——那些应该变成 commit message、代码注释或 notes 文件。砍回指针形式。

一份太长的简报会被略读，而被略读掉的那部分，正好就是藏地雷的地方。

## 放在哪

默认输出在对话里，方便你粘贴到新会话。只有你明确要求时才写文件，并且优先放在仓库里本来就有的位置（PR 描述、`NOTES.md`），而不是随手发明一个路径。

## 怎么改成适合你的

如果你们的任务总带某些固定信息（比如线上事故编号、灰度环境地址、on-call 交接），把它们加成固定小节。**判断标准是：如果少了这一条，下一个会话会做出错误动作**——满足这个条件才值得固定进模板。
