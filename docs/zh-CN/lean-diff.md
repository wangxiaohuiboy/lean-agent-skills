# lean-diff

> 能用一行解决的，不要写十行。但「小改动」的前提是先把问题真正搞懂。

## 它解决什么问题

模型在写代码时的默认倾向是**过度完成**：一个需求进来，它倾向于交出一个框架。常见的几种：

- 加一个只有一种实现的接口，或者只有一个产品的工厂。
- 为一个只在一处使用的值引入配置层。
- 为了一个函数装一个依赖。
- 修 bug 的时候顺手重构周边代码。
- 为不可能出现的状态写错误处理。

这些都不算错，但都让改动变大、评审变慢、回归面变大。

## 什么时候会触发

功能开发、修 bug、重构——只要「范围控制」这件事值得有人管的时候。以及当之前的尝试明显做过头了，你想往回拉的时候。

## 核心规则

### 七级解法阶梯，停在第一个成立的

1. **这东西需要存在吗？**（YAGNI）可能一个已有功能、一个手动步骤就够了。先说出来，再给更小的方案。
2. **这个仓库里已经有人做了吗？**先 grep，再写。
3. **标准库有吗？**`Intl`、`pathlib`、`URL`、`structuredClone`、`crypto.randomUUID`。
4. **平台能力覆盖吗？**原生 `<dialog>`、CSS `clamp()`/`:has()`、`fetch`、`AbortController`、数据库约束。
5. **已经装了的依赖里有吗？**
6. **能是一行，或者改个配置吗？**
7. **才写最小可用代码。**

### 阶梯的前提：先理解，再爬

这是这份文档里最容易被忽略、也最重要的一句：**阶梯是在你理解问题之后才开始爬的，不是用来替代理解。**

读任务涉及的代码，把真实的调用链走通。一个位置放错的小改动不是「效率」，它是第二个 bug。

### 修 bug 就是修根因

拿到一份 bug 报告，先做三件事：

1. `rg -n 'functionName\('` 找出这个函数的所有调用方。
2. 判断这个不变量真正该待在哪里。
3. 在最窄的共享点上修一次。

只修报告里点名的那条路径，会留下一堆同样坏掉的兄弟调用——那不是小改动，那是没做完。

### 主动降级必须标注

当你明知有上限还是选了便宜的方案（全局锁、O(n²) 扫描、朴素启发式、写死的地区），留一行注释写清上限和升级路径：

```js
// lean: 全局锁，1k req/s 以下够用。升级：按 key 分片。
```

这一行是「主动权衡」和「没意识到」之间的分界线。

## 明确不省的东西

省的是代码量，不是严谨程度。以下永远不在砍的范围内：

- 信任边界上的输入校验。
- 防止数据丢失的错误处理。
- 安全、无障碍。
- 用户明确要求的行为。
- 真实平台的行为：时钟漂移、传感器校准、部分失败、网络不可用。

当两个标准库方案体量相同时，选边界情况正确的那个。**精简意味着更少的代码，不是更脆的算法。**

## 什么情况下别用它

不是所有事都该省。新服务、需要长期稳定的对外 API、数据迁移、安全边界——这些值得真正的结构。`references/ladder-examples.md` 里最后一节专门写了这个边界。

## 效果对比

**过度完成**：为「加一个日期格式化」写一个 `DateFormatter` 类，带 locale 配置，拆一个 `formatters.ts`，配上单元测试。

**阶梯第 3 级**：

```js
new Intl.DateTimeFormat(locale, { dateStyle: 'medium' }).format(date)
```

**过度完成**：为防抖一个搜索框 `npm i lodash`。

**阶梯第 7 级**：八个字以内能写完的函数，零依赖，并且处理了朴素实现会漏掉的两个细节（保留最新参数、取消挂起的调用）。

## 怎么改成适合你的

**改「不省」清单，别改阶梯。**七级阶梯是通用判断顺序，真正需要按团队调整的是那份「永远不省」的清单——比如你们特别在意的审计日志、权限边界、金额精度。把它写具体，比写「注意质量」有用一百倍。
